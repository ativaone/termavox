Help

How Termdock looks after your sessions, what each status and notice means, and where everything is.

{{index-inline}}

The essentials

The session lives in Termdock, not in the browser. Termdock keeps every session open on its own server. The browser only shows it: close the tab, shut the laptop or switch to your phone, and the terminal is exactly as you left it when you come back, with vim or htop still running.

Closing doesn't end anything
Closing a tab, a pane or the browser only detaches the view. The session keeps running until you use End.
Protected sessions ride out drops
With tmux on the server, a session survives network drops and Termdock restarts. The shield next to it says whether it is protected.
tmux stays invisible
Termdock uses tmux underneath, with no status bar and no prefix key. Scrolling, selection and copy are the browser's own.

Two sessions on the same server can react differently to the same drop. It depends on whether the session is protected (filled shield) or not protected.

“The server restarted” isn't always a reboot

The notice shows whenever Termdock reconnects and the session's tmux no longer exists. It may have been a reboot, but also a tmux killed by hand or by the system (when it ran out of memory, for example) while the session was disconnected.

tmux kill-server inside the session doesn't take the session down

Termdock's tmux uses a socket of its own, separate from yours: tmux kill-server only closes your tmux. pkill tmux and killall tmux, though, kill every tmux of the user, the session's included.

Not protected and no new shell

The new shell depends on Reopen unprotected sessions automatically, under Advanced on the server's page (on by default). When it is off, the session moves to Ended instead.

Protected sessions

A protected session runs inside a tmux on the server, which Termdock drives without showing it. If the connection drops or Termdock restarts, tmux holds on to the shell and its programs, and Termdock rebuilds the screen from it.

The shield next to each session says which case it is; hover it to read:

  • Filled: “Protected: survives restarts and network drops”.
  • Struck through: “Not protected: the shell is lost if the connection drops”. The session keeps running with the browser closed; what it can't survive is losing its connection to the server.
  • Dashed: “Protection is decided when the session starts”.

To protect its sessions, the server needs tmux 3.2 or newer and a UTF-8 locale, with Session protection set to Auto (the default) on the server's page. Under Diagnostics → Test connection, the server's page shows what it has and what is missing.

Protection is decided when the session starts

Installed tmux later? New sessions start protected; the ones already running stay as they were. If a reconnect no longer finds tmux, the session loses its protection and says so: it never changes silently. The Activity page shows each session's protection.

“The server may kill tmux on disconnect”

Some servers (systemd-logind with KillUserProcesses=yes) kill the user's processes when the SSH login ends, tmux included. With that notice on the server's page, enable linger for the user (loginctl enable-linger) and make sure systemd-run exists; without it, protection isn't reliable.

You don't need a tmux of your own

It works, but with a tmux inside the session, scrolling, selection and copy become tmux's instead of the browser's. The pane says so when it sees one; the tip can be turned off under Settings → Terminal.

Two different connections

  • Your connection (browser ⇄ Termdock). When it drops, a strip says “Offline, retrying”. Sessions feel nothing; the screen catches up when it is back.
  • The session's connection (Termdock ⇄ server). When it drops, the pane shows “Reconnecting…”. This is the one protection covers.

When the session's connection drops:

  • A session that never connected tries a few times and stops: it is almost always a wrong address, port or credential. Fix it on the server's page and use Retry; the fix is used by the next attempt.
  • A session that was connected keeps trying for up to 30 minutes; the pane shows until when. After that it is Disconnected.
  • Retry now skips the wait. Stop ends the attempts.

Disconnected isn't lost

In a protected session, tmux keeps running on the server while the session is Disconnected, even after Stop. When the server is back, Retry finds the same screen.

“Termdock was updated”

After an update, reload the page to load the new version. Sessions keep running meanwhile.

Close, end, reopen and remove

  • Closing a tab or a pane only detaches the view. The session stays in the list, running.
  • End… (the session's menu) stops the shell and every program on the server. If the server is down, the session ends at once and its tmux is ended by the next connection to that server.
  • End all sessions…, at the foot of the list, does the same for every running session.
  • Reopen brings an ended session back with a new shell, keeping its name.
  • Remove from list… (ended sessions only) deletes the session and its history. Remove all ended… does that in one go.

End can't be undone

A deploy in progress, a vim with unsaved changes: everything stops on the server. Only leaving? Close the tab, the pane or the browser.

One session in several places

Open the same session on your laptop, another computer and your phone at the same time: they all see the same screen and they can all type.

The terminal's size follows the window where someone last typed or clicked. The others show the session scaled down or letterboxed, with “Sized by another window. Click to fit.”

Back from the phone and the screen is narrow?

Click the terminal: it goes back to this window's size, and programs like vim and htop redraw.

Workspace and shortcuts

  • The list on the left groups sessions by status. The button right under New session collapses the list into a column of icons.
  • Split a tab with Split right and Split down, and drag the divider to adjust. Open in a new tab is in the session's menu.
  • Rename a session from its menu, or double-click its tab. Everyone who sees the session sees the new name.
  • Tabs, splits and sizes are stored in Termdock and come back in any browser you sign in to.

With a terminal focused, the keys belong to the terminal

Apart from the finder shortcut, nothing in Termdock intercepts the keyboard inside a terminal.

Copy, paste and links

Under Settings → Terminal:

  • Copy on select (off by default): selected text goes to the clipboard right away.
  • Paste with right click (off): right click pastes instead of opening the browser menu.
  • Confirm before opening links (on): a link clicked in the terminal shows its full address before it opens in a new tab.

OSC 52 lets remote programs write to your clipboard

When it is on, vim or tmux on the server can overwrite what you copied, without asking. Leave it off unless you need it.

On a phone

  • The session list fills the screen; a session opens full screen, and Sessions goes back to the list.
  • The key bar has Esc Tab Ctrl Alt, the arrows, the pipe and Paste.
  • Ctrl and Alt stay armed for the next key: tap Ctrl, then c, to send Ctrl+C.
  • If the browser doesn't let the bar paste, long-press the terminal.
  • You can install Termdock as an app from the browser's menu (“Add to Home screen”).

File panel

The Files button on a session's pane opens the server's files beside the terminal. It uses the session's own SSH connection, as the same user: no second sign-in and nothing installed on the server. That is also why it works only while the session is connected.

  • Upload several files at once, or drag and drop them on the panel. Download, Rename and Delete act on the selected items; New folder is at the top.
  • When a file already exists: Replace (keeps the current file's permissions), Keep both or Skip these.
  • Go to the terminal's folder exists in protected sessions only.
  • Whole folders can't be uploaded or downloaded yet: select the files inside them.
  • Keyboard: the arrows move, Space selects, Enter opens a folder, F2 renames, Delete deletes.

Deleting a folder deletes everything inside it, on the server

This can't be undone. Links are deleted as links: their targets are not touched.

The panel says the server doesn't offer SFTP?

Whoever runs the server must enable Subsystem sftp internal-sftp in sshd_config and reload sshd. If the Files button doesn't show anywhere, the Termdock administrator turned the panel off.

Servers and credentials

  • A server holds everything an ssh user@address needs: the address, port, user name, credential and the session options. The same machine with another user is another server; Duplicate helps.
  • Changes to a server apply to new sessions. The running ones keep the address they started with.
  • To sign in, prefer Generate a new key: the private key never leaves Termdock, and you install the public key on the server. You can also paste a key, use a password, or choose None (the server asks for the password in the terminal).
  • Under Advanced: protection, startup command, environment variables, keepalive, scrollback lines and reopening unprotected sessions.
  • Termdock runs in Docker on the same machine you want to reach? Use Add this Docker host.

Secrets show only once

Once saved, passwords and private keys never come back to the browser, and a generated public key is shown only when it is created. Copy it right away.

Host keys and server sign-in

  • On the first connection Termdock asks Trust this host key?. Compare the fingerprint with the server's (there, ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub) before you trust it.
  • The decision applies to the address: every one of your servers at that address, and only for you.
  • To trust a key before the first session, use Test connection or Paste expected fingerprint on the server's page.
  • Servers that ask for a code (2FA) or a password show the question in the pane. Answers go to the server and are never stored. If the prompt expires, use Retry.

“Host key changed”

Someone may be intercepting the connection, and Termdock refuses to connect; there is no way to accept it there. If you know the server was reinstalled or changed its key, go to the server's page and use Replace trusted key, typing the address to confirm. When in doubt, don't connect.

Sessions left running on a server

A protected session's tmux keeps running on its server while Termdock is down. That is on purpose: when Termdock is back, it reconnects to it. It is only left behind when Termdock forgets it: another Termdock installation, or this one after its database was reset.

  • The workspace says Sessions found on… when it sees one of these while connecting.
  • On the server's page, Sessions on this server → Check now lists them. Adopt brings one into the workspace, with the same screen; End… stops its programs.
  • Sessions you had already ended that were still running there are ended automatically.

Account and administration

  • Password (Settings → Account): changing it signs out your other browsers. Forgot it? Ask an administrator for a temporary password.
  • Two-step verification: a code from an authenticator app at every sign-in. An administrator can make it required.
  • Language: in the account menu, under Language….
  • Activity shows what happened to your sessions. Terminal input and output are never recorded.
  • Administrators create users, can require two-step verification, cap the running sessions per user (default: 50), turn the file panel on or off and read the audit log.
